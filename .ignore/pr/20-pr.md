## 変更内容

- **documentsテーブル**: `document_id`（PK・呼出側採番）・`tenant_id`（仮置き: 固定値 `default`）・`document_type`（text+CHECK制約）・`blob_ref`・`content_sha256`・受領/作成日時。単一テーブル+種別列は統合モデル採否未確定のための仮置き（`docs/data-model/documents.md` に明記）
- **DB層**: SQLAlchemy 2.0（同期）+ psycopg3 + Alembic。マイグレーション（`api/migrations/`）を正とし、テストも `alembic upgrade` でスキーマ構築
- **Blobアダプタ**: `BlobStorage` Protocol + `AzureBlobStorage`（Managed ID・overwrite不可）/ `LocalFileBlobStorage`（ローカル開発）。テストはインメモリフェイク
- **`POST /api/documents`**（multipart・JWT必須）: 201新規 / 200冪等再送（sha256+種別一致）/ 409内容不一致 / 415非PDF（content-type+マジックバイト検査）/ 422不正種別 / 401未認証。同時登録競合はPK違反を捕捉して冪等判定へフォールバック
- **realm**: M2M連携用confidentialクライアント `factone-integration`（client credentials grant・audienceマッパー）追加。シークレット設定スクリプトを `apply-keycloak-secrets.sh` へ汎用化（テストユーザーパスワード+クライアントシークレット）
- テスト9件追加（実PGコンテナ接続。`factone_test` DBを自動作成）
- `docs/data-model/documents.md` 新規、develop-guide更新（マイグレーション手順・M2Mトークン取得）、API契約再生成

## DB層の技術選定理由（記録）

- **SQLAlchemy 2.0（ORM・クエリビルダ）** — テーブル定義のPythonコードでの単一情報源化、型付きクエリ、セッション/トランザクション管理。Pythonデファクトで実績最多、2.0の型システム刷新でmypy strictと親和、Alembicとネイティブ統合。
  - 代替案: SQLModel（Pydantic統合は魅力だが薄いラッパで成熟度劣。SQLAlchemy知識はどのみち必要）、素psycopg+手書きSQL（スキーマ定義とクエリの二重管理・migration自作）
- **psycopg3（DBドライバ）** — DB接続・SQL実行・型変換の最下層。psycopg2の公式後継で活発メンテ、SQLAlchemy公式対応。同期/非同期両対応のため将来async移行時もドライバ据置。
  - 代替案: psycopg2（メンテナンスモード）、asyncpg（非同期専用で同期方針と不整合）
- **Alembic（スキーママイグレーション）** — DDL変更の履歴管理・適用順序制御・autogenerate。SQLAlchemy作者製で統合最良。「マイグレーションが正」の運用が素直に組める。
  - 代替案: 手書きSQLスクリプト（履歴・順序・適用状態管理の自作が必要）
- **同期採用の理由**: PoC負荷では非同期の複雑性（セッション管理・テスト）に見合う利点がない。FastAPIのthreadpool実行で十分。
