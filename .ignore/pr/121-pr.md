# 概要

IDP 実行結果の取得 API を「一覧（サマリ）/ 詳細 / 最新」に分割し、応答サイズが実行回数に比例して肥大する問題を解消する。Viewer の作業パネルを一覧→詳細取得の流れに追従させる。

## 関連Issue

Closes #114

## 変更内容

- `GET /api/v1/documents/{document_id}/idp-runs`: 応答を `IdpRunSummary`（`run_id` / `document_id` / `run_type` / `status` / `executed_at` / `di_api_version` / `di_model_id` / `error_info`）の配列に縮小。順序は現状維持（`executed_at` 昇順）
- 新設 `GET /api/v1/documents/{document_id}/idp-runs/latest`: 最新の成功実行を詳細で返す（`executed_at` 降順・同時刻は `id` 降順）。任意クエリ `run_type=initial|rerun` で絞込。該当なしは 404 `idp-run-not-found`。`{run_id}` ルートより先に宣言
- 新設 `GET /api/v1/documents/{document_id}/idp-runs/{run_id}`: 詳細（`IdpRunResponse`）。他文書・不在は 404 `idp-run-not-found`
- `IdpRunResponse` は `IdpRunSummary` を継承。`_to_summary` / `_to_response` で一覧と詳細を組み立て
- テスト: 一覧から項目値・テーブル等を読んでいた既存テストを詳細取得へ書き換え、サマリ一覧・詳細・latest・認証のテストを追加
- Viewer `WorkPanel`: 履歴は一覧サマリで描画し、選択行の詳細を `run_id` キーでキャッシュしながら取得。IDP実行の応答は詳細と同形のためそのまま選択状態にする。表示・data-testid は不変。詳細取得の応答待ち中に別の実行を選択した場合は古い応答を捨て、取得済み実行の再選択で残存エラー表示を消す
- API 契約生成物（`docs/api/openapi.json`・`viewer/src/api/schema.d.ts`）の再生成
- ドキュメント: `docs/data-model/idp-runs.md`（API 一覧）、`docs/api/README.md`（v1 内破壊的変更の記録）、ADR-0017 追記（外部利用者接続前の例外）

## 動作確認方法

1. `podman compose up -d postgres` → `cd api && uv run pytest`（174 件通過）、`cd viewer && npm run test && npm run build`
2. 文書登録 → IDP 実行を 2 回 → `GET …/idp-runs` の各要素に `raw_fields` 等が含まれないこと → `GET …/idp-runs/latest` が 2 回目の結果を返すこと → `?run_type=initial` で 1 回目が返ること → `GET …/idp-runs/{run_id}` で詳細が返ること
3. Viewer で文書を表示: 実行履歴の行選択で読取結果が切り替わり、同じ行の再選択で詳細 API が再呼出されないこと（DevTools の Network）

- `IdpRunSummary` の `base_run_id` / `corrected_by` は #115 で追加する
