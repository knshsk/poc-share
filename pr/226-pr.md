# 概要

見積書のシードの2種別（`quotation`・`quotation_di`）で、担当者の項目が宛先の担当者を指していた問題を直す。見積書に載る担当者は、見積書を発行した自社の営業担当者である。そこで、`CustomerContactPersonName`（取引先担当者）を`SalesPersonName`（営業担当者）に改める。

## 関連Issue

Closes #225

## 変更内容

- マイグレーション`332ca49b6d4f`を追加した。対象は、`tenant_id`が`default`の`quotation`・`quotation_di`だけである。注文書の種別と既存の実行結果は変えない
  - `CustomerContactPersonName`の項目を、並び順を変えずに、キー`SalesPersonName`・ラベル「営業担当者」に書き換える。型（string）と表示有無は変えない
  - `quotation`（CU）の説明を`Name of the sales person in charge at the company that issued this quotation.`に改める。`quotation_di`には今までどおり説明を付けない
  - downgradeで元のキー・ラベル・説明に戻す
- テスト: マイグレーションのテストに1件追加した。`default`の見積書の2種別だけが変わること、ほかの種別と`other`テナントが変わらないこと、downgradeで戻ることを確かめる
- ドキュメント: `docs/data-model/document-type-configs.md`のシードデータに、見積書の2種別では`SalesPersonName`を使うことを書いた。ADR-0029の追記にも理由を足した。`conftest.py`のテスト用の種別のコメントを直した

## 動作確認方法

1. `cd api && uv run pytest tests/test_migrations.py`を実行し、すべて通ることを確かめる
2. ローカルのDBで`uv run alembic upgrade head`を実行する。`GET /api/v1/config/document-types`で、`quotation`・`quotation_di`の7番目の項目が、キー`SalesPersonName`・ラベル「営業担当者」になっていることを確かめる。`quotation`の説明が発行元の営業担当者を指していることも確かめる。`purchase_order`・`purchase_order_di`は`CustomerContactPersonName`のままである
3. `uv run alembic downgrade f1a6c3e8b2d4`で、元のキー・ラベル・説明に戻ることを確かめる

## 備考

- 外部システムが見積書から担当者を読むキーは、`CustomerContactPersonName`から`SalesPersonName`に変わる。CUとDIの種別でキーがそろっている点は変わらない
- CUのアナライザは、項目の定義が変わるため、次回の実行時に置き換わる
- 実行ログの`fields`は、実行時点のキーとラベルを持つ。そのため、このマイグレーションより前の見積書の実行結果では、`CustomerContactPersonName`が元のラベル「取引先担当者」のまま、Viewerのキー項目の末尾に表示される。新しい項目で表示するには、IDPを実行し直す
