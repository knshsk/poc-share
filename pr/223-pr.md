# 概要

書類の読取（項目の抽出）を、DIの`prebuilt-layout`とQuery Fieldsに固定した形から切り離し、文書種別ごとに読取エンジンを選べるようにする。2本目のエンジンとしてAzure AI Content Understanding（CU）を加え、明細をオブジェクトのリストとして抽出・表示・修正できるようにする。シードの注文書・見積書はCUの種別にし、DIの種別は`purchase_order_di`・`quotation_di`の種別コードで残す。

統合ブランチ`feature/213-engine-neutral-extraction`を`main`へ取り込むPRである。子Issueの変更は、それぞれのPR（#217・#219・#220・#222）でレビューを受けて、統合ブランチに取り込んである。

## 変更内容

- 抽出エンジンの境界（#214）
  - 文書種別設定に`engine`（`azure-di` / `azure-cu`）を追加した。1回の実行では1つのエンジンを呼ぶ
  - 項目に`description`を追加した。`azure-di`の種別は、項目を20件までとする
  - 実行ログ（`idp_runs`）の項目値を`fields`の1列にまとめた。`di_api_version` / `di_model_id`は`engine` / `engine_info`に、`tables`は`layout_tables`に改めた。人手修正のボディの`table_cells`は、`layout_table_cells`に改名した
  - 生値はエンジンが読んだ原文とし、正規化値は今と同じ規則で生値から作る（ADR-0029）
- CUのアダプタと明細（#215）
  - CUのアナライザは、テナントと文書種別の組ごとに1つ持つ。実行のたびに定義のハッシュで文書種別設定とのずれを検出し、ずれていれば置き換えてから解析する（ADR-0030）
  - 項目の型に`array`（明細）を追加した。応答の項目値と人手修正のボディに、明細の値（`items`）を加えた。明細の修正は値だけで、行の追加・削除はできない
  - BicepにCUのリソース（キー認証は無効）と、gpt-4o・text-embedding-3-largeのデプロイを追加した。APIのManaged IDへのロールと、Container Appの環境変数も追加した
  - 不要になったアナライザを消す運用スクリプト`api/scripts/cleanup_cu_analyzers.py`を追加した
- Viewerの明細（#216）
  - 右ペインに、明細の区分（表と、選択中の値の詳細欄）を加えた。明細の値は、キー項目と同じく修正・確定できる。キャンバスの読取矩形とは、相互にハイライトする
- シードの文書種別（#221）
  - `default`テナントのDIの`purchase_order`・`quotation`を、`purchase_order_di`・`quotation_di`に改名した。参照する文書の`document_type`も書き換える
  - CUの`purchase_order`・`quotation`を追加した。ヘッダ項目のキーはDIの種別と同じで、明細の項目`LineItems`を持つ。見積書の2種別には、版数`RevisionNumber`を加えた
- ドキュメント: ADR-0029・ADR-0030を起票し、ADR-0017・ADR-0019・ADR-0022に追記した。`docs/`のarchitecture・azure・data-model・api・viewer・develop-guideを更新した

## 動作確認方法

1. `cd api && uv run pytest`と`cd viewer && npm run test`を実行し、すべて通ることを確かめる
2. ローカルのDBで`uv run alembic upgrade head`を実行する。`GET /api/v1/config/document-types`が、CUの`purchase_order`・`quotation`（`engine`が`azure-cu`、`fields`の最後が`LineItems`）と、DIの`purchase_order_di`・`quotation_di`を返すことを確かめる
3. 明細の画面の表示と修正は、Viewerの単体テスト（`viewer/tests/item-table.test.ts`・`viewer/tests/result-editor.test.ts`）で確かめる

IDP実行はDI・CUの課金が発生するため、確認に含めない。

## 備考

- 外部システムへの影響
  - ヘッダ項目は、これまでと同じく`fields.<キー>.normalized_value`（生値は`value`、確信度は`confidence`）で読める。シードの種別のヘッダ項目のキーも変わらない
  - 最上位の`tables`が`layout_tables`に、`di_api_version` / `di_model_id`が`engine` / `engine_info`に変わる。CUの種別では、`layout_tables`が空配列になり、`fields`に明細の項目`LineItems`（`items`を持ち、`normalized_value`を持たない）が加わる
  - これらは、外部連携システムが接続するまでのv1内の破壊的変更として扱う（ADR-0017の追記）
- #213の完了条件に従い、このPRのマージ前に、統合ブランチを検証環境にデプロイして確かめる。デプロイは`build-images.sh`と`deploy-apps.sh`で行い、CUのリソースも同じデプロイで作られる。対象のリージョンには、gpt-4oのStandardの容量（30）の空きが要る
- 既知の残件: #218（金額の末尾に締めの記号が付くと、正規化値がnullになる）。CUは帳票の「－」を`-`や`ー`で返すため、CUの種別でも起きる
