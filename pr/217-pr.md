# 概要

読取エンジンを差し替えられるように、抽出エンジンの境界をエンジンに依存しない形にし、Document Intelligence（DI）をその上に載せ替える。文書種別設定に抽出エンジン（`engine`）と項目の説明（`description`）を追加し、実行ログとAPIの形をDI固有の名前からエンジンに依存しない名前へ改める。DIの抽出結果と、Viewerの読取結果・修正・ハイライトの挙動は変えない。

このPRは統合ブランチ`feature/213-engine-neutral-extraction`に向ける。 #215 、 #216 とそろえてから`main`へ取り込む（#213）。

## 関連Issue

Closes #214

## 変更内容

- 抽出エンジンの境界（`api/app/services/engine.py`）を新設した。呼出口は`DocumentAnalyzer.analyze(pdf, schema, schema_owner)`で、入力をQuery Fieldsのキー名の列から文書種別設定のスキーマに変えた。`schema_owner`はテナントIDと文書種別コードの組で、スキーマの事前登録が要るエンジンが使う（DIは使わない）。結果の型（`AnalysisResult`・`LeafResult`・`LayoutTable`）と例外（`EngineError`）もここに置いた
- DIのアダプタ（`api/app/services/di.py`）を新しい境界に合わせた。スキーマの`key`をQuery Fieldsに渡す。呼び方（prebuilt-layoutにQuery Fieldsを付ける）は変えていない
- `create_app`は、エンジン名から実装を引く表（`app.state.document_analyzers`）を組み立てる。`FACTONE_DI_ENDPOINT`が設定されているときだけ`azure-di`を登録する。IDP実行は文書種別設定の`engine`で表を引き、表に無いエンジンは未設定として扱う。このときはfailed行を残して502 `document-analysis-failed`を返し、`error_info`は`azure-di endpoint is not configured`になる
- 文書種別設定の変更
  - `engine`（varchar(20) NOT NULL、既定値`azure-di`）を追加した。値は`azure-di`だけを受け付ける。PUTで省略すると`azure-di`になる
  - `fields[].description`を追加した。省略でき、指定するときは1〜1024文字とする。NULを含むと422 `validation-error`
  - `engine`が`azure-di`の種別は、項目を20件まで（DIのQuery Fieldsの上限）とした。超える設定の作成・更新は422 `validation-error`で、理由は`errors[].msg`に入る
- 実行ログ（`idp_runs`）の変更
  - 項目値の5列（`raw_fields` / `normalized_fields` / `confidence` / `field_labels` / `field_regions`）を、項目ごとの値（`label` / `value` / `normalized_value` / `confidence` / `region`）をまとめた`fields`の1列にした
  - `tables`を`layout_tables`に改名し、`di_api_version` / `di_model_id`を`engine` / `engine_info`に置き換えた。`engine`は失敗した実行にも入り、修正行はbaseからコピーする
  - マイグレーションは3本（`a1e5c8f2d7b4`・`b6d2f9a4c8e1`・`e8c3a7d5f1b2`）。既存の行は`engine='azure-di'`として移し、保存済みの修正（`corrections`）の`table_cells`は`layout_table_cells`に書き換える。DIの行はdowngradeで元の列に戻せる。ラベル列がNULLだった旧い行は、`{key: null}`のラベル列として戻る
- APIの変更（v1内の破壊的変更。外部連携システムは未接続で、ADR-0017の例外の範囲）
  - 実行結果の一覧・詳細の`di_api_version` / `di_model_id`を、`engine` / `engine_info`に置き換えた
  - 詳細の`tables`を`layout_tables`に改名した。OpenAPIのスキーマ名は`LayoutTable` / `LayoutTableCell`になった
  - 修正のボディの`table_cells`を`layout_table_cells`に改名した（スキーマ名は`LayoutTableCellCorrection`）
  - 項目値の形（`fields[key]`）と、`verbose`によるキーの出し分けは変えていない
- Viewer: 新しい名前（`layout_tables` / `layout_table_cells`）に追従した。挙動は変えていない
- テストの追加・更新
  - エンジンの選択（表に無いエンジンでfailed行と502）、DIアダプタの組立、スキーマと持ち主の受け渡しを確かめる
  - 文書種別設定では、項目20件は保存でき21件は422になること（POST・PUT）、`description`の長さ・空文字・NUL、PUTで`engine`を省略したときの既定値を確かめる
  - マイグレーションでは、旧い形の行（ラベルの無い成功行・失敗行・修正行）が新しい形に移り、downgradeで戻ることを確かめる
  - 応答では、`engine` / `engine_info` / `layout_tables`と、旧いキーが無いことを確かめる
- ドキュメント: ADR-0029（抽出エンジンを文書種別の単位で選び、エンジン非依存のスキーマと結果の契約を置く）を起票し、ADR-0017・ADR-0019・ADR-0022に追記した。`docs/data-model/`（idp-runs・document-type-configs）、`docs/architecture/`（api・overview・viewer）、`docs/viewer/`（result-panel・display）、`docs/api/README.md`、`api/README.md`を更新した

## 動作確認方法

自動テストは、`api/`で`uv run pytest`、`viewer/`で`npm run test`を実行する。

既存の実行ログの移行は、IDP実行の結果と修正行を持つ文書がある手元のDBで確かめる。DIの呼出（課金）は行わない。

1. このブランチで`api/`から`uv run alembic upgrade head`を実行する
2. Viewerでその文書を開き、読取結果タブのキー項目・候補値・表、修正済みのマーク、キャンバスとの相互ハイライトが、適用前と同じに表示されることを確かめる
3. 表のセルを1つ修正して確定する。確定後の結果で、修正したセルの右上に修正済みの印（三角）が付くことを確かめる
4. `GET /api/v1/documents/{document_id}/idp-runs/latest?verbose=true`の応答に`engine`（`azure-di`）・`engine_info`・`layout_tables`があり、`di_api_version` / `di_model_id` / `tables`が無いことを確かめる。修正行の`corrections`は`layout_table_cells`を持つ
5. `uv run alembic downgrade c4d931791740`の後に`uv run alembic upgrade head`を実行し、手順2と同じ表示に戻ることを確かめる

未設定のエンジンの扱いは、`FACTONE_DI_ENDPOINT`を設定していないAPIでIDP実行を押して確かめる。502になり、実行履歴に失敗行が追加され、エラー情報は`azure-di endpoint is not configured`になる。

文書種別設定の検査は、`POST /api/v1/config/document-types`で確かめる。項目を21件にすると422 `validation-error`になり、`errors[].msg`に`at most 20`が含まれる。20件なら201になる。
