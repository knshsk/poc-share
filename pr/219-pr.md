# 概要

2本目の抽出エンジンとして、Azure AI Content Understanding（CU）を`azure-cu`で加える。あわせて、項目の型に明細を表す`array`を加え、明細をオブジェクトのリストとして抽出・保存・修正できるようにする。CUのリソースとモデルのデプロイはBicepで追加し、不要になったアナライザを消す運用スクリプトを加える。`azure-di`の種別の抽出結果と応答は変えない。

このPRは統合ブランチ`feature/213-engine-neutral-extraction`に向ける。 #216 とそろえてから`main`へ取り込む（#213）。

## 変更内容

- CUのアダプタ（`api/app/services/cu.py`）を追加した
  - アナライザは、テナントと文書種別の組ごとに1つ持つ。IDは`factone_`にテナントIDと文書種別コードのハッシュを付けたもので、テナント間で共有しない
  - アナライザのタグに定義のハッシュを持たせる。実行のたびにアナライザを取得し、無い・ハッシュが違う・`ready`でないときは作成（置き換え）してから解析する
  - CUは、リソースの既定（モデルの別名とデプロイの対応）が未設定だとアナライザの作成を拒否する。そのため、アダプタが作成の直前に既定を設定する。解析のリクエストでも、別名とデプロイの対応を渡す
  - 生値は、CUが根拠として示す全文中の範囲（spans）から切り出した原文とする。正規化値は今と同じ規則で作る。読取領域は、先頭の領域と同じページにある領域の外接矩形とする
  - 認証はEntra（`DefaultAzureCredential`）だけとする。`processingLocation`は`geography`を指定する
  - CUの呼出の失敗と想定外の応答は、DIと同じくfailed行を残して502 `document-analysis-failed`を返す。解析の最終応答（生応答）はBlobに保存し、CU側の解析結果は削除する
  - 環境変数`FACTONE_CU_ENDPOINT` / `FACTONE_CU_COMPLETION_DEPLOYMENT` / `FACTONE_CU_EMBEDDING_DEPLOYMENT`を追加した。`FACTONE_CU_ENDPOINT`が設定されているときだけ、抽出エンジンの表に`azure-cu`を登録する
- 文書種別設定の変更
  - `engine`に`azure-cu`を追加した
  - `fields[].type`に`array`を、`fields[].properties`（明細の列）を追加した。プロパティの型は`string` / `number` / `date`に限り、入れ子は1段までとする。`array`の項目にはプロパティが1件以上必要である。プロパティが無い場合、プロパティのキーが重複する場合、`array`以外の項目に`properties`を指定した場合は、422 `validation-error`になる
  - `azure-di`の種別には`array`を指定できない（422 `validation-error`）。項目数の上限（20件）は`azure-di`だけに掛かる
- 実行ログ（`idp_runs.fields`）と応答の変更
  - `array`の項目は`items`を持つ。`items`の各行は、プロパティのキーごとに、スカラーの項目と同じ形の値（`value` / `normalized_value` / `confidence`）を持つ。`verbose`では、項目の`label`と`property_labels`、各値の`region`を加える。OpenAPIでは、項目値が`FieldResult | ItemsFieldResult`のunionになる
  - 修正のボディに`items`（`field` / `index` / `property` / `value`）を追加した。修正は項目・行・プロパティの組ごとに累積する。明細の行の追加・削除はできない
  - 明細の修正を加える前に保存された修正行では、`verbose`の応答で`corrections.items`を空の配列で補う
  - マイグレーション`b6d2f9a4c8e1`のdowngradeは、明細の値を持つ行があると例外で止まる（旧い列では表現できないため）
- Viewer: 項目値のunionに追従し、明細の項目を読取結果のキー項目とキャンバスのハイライトから除いた。明細の表示・修正は #216 で行う
- Bicep: CUのリソース（`modules/content-understanding.bicep`、キー認証は無効）と、gpt-4o（2024-11-20、Standard）・text-embedding-3-large（Standard）のデプロイを追加した。APIのマネージドIDにCognitive Services Userロールを付け、Container Appに環境変数を渡す
- 運用スクリプト`api/scripts/cleanup_cu_analyzers.py`を追加した。DBの`azure-cu`の文書種別設定のどれにも対応しないアナライザを消す。既定では候補の表示だけを行い、`--apply`で削除する。`azure-cu`の設定が0件のときは、接続先のDBを取り違えたおそれがあるため、`--apply`を付けても削除しない。APIのコンテナイメージに同梱する
- テストの追加・更新
  - 文書種別設定では、`array`とプロパティの規則と、DIの種別で`array`を拒むことを確かめる
  - 抽出結果の組立・修正では、明細の各行にスキーマのプロパティがそろうこと、エンジンが想定と違う形を返した項目の扱い、明細の修正の累積を確かめる
  - 応答では、明細の値と、`items`の無い旧い修正行で`corrections.items`が空の配列になることを確かめる
  - CUアダプタでは、アナライザの同期の分岐（作成・再利用・置き換え・作成の失敗）、作成前の既定の設定、実際の応答のサンプルからの変換、読取領域の2つの形と外接矩形、ポーリングの失敗と想定外の応答の`EngineError`への変換を確かめる
  - マイグレーションでは、明細の値を持つ行でdowngradeが止まることを確かめる
- ドキュメント: ADR-0030（CUのアナライザをテナント×文書種別ごとに持ち、実行時に文書種別設定とそろえる）を起票し、ADR-0017・ADR-0029に追記した。`docs/azure/`、`docs/data-model/`（idp-runs・document-type-configs）、`docs/architecture/`（api・overview・viewer）、`docs/viewer/`（result-panel・display）、`docs/develop-guide/`（api・deploy）、`docs/api/README.md`、`api/README.md`を更新した

## 動作確認方法

自動テストは、`api/`で`uv run pytest`、`viewer/`で`npm run test`を実行する。テストでは、CUの呼出をモックに置き換え、実サービスは呼ばない。

実サービスでの確認には、CUのリソースとデプロイが要る（課金は呼出の分だけ）。`bicep/modules/content-understanding.bicep`を含むコアインフラをデプロイするか、既存のCUリソースを使う。手元のAPIから呼ぶ場合の設定は、`docs/develop-guide/api.md`の「Content Understanding接続」に従う。

1. `POST /api/v1/config/document-types`で、`engine`を`azure-cu`にし、ヘッダの項目（`string` / `number` / `date`）と、`array`の項目（プロパティ数件）を持つ文書種別を作る。`description`には、項目の意味を書く
2. その種別で注文書などのPDFを登録し、IDP実行を行う。初回はアナライザの作成を含むため、DIより時間がかかる
3. `GET /api/v1/documents/{document_id}/idp-runs/latest?verbose=true`で、ヘッダの項目に値・正規化値・信頼度・`region`が入り、`array`の項目の`items`に行ごとの値が入ることを確かめる。`engine`は`azure-cu`で、`engine_info`にアナライザのIDと定義のハッシュが入る
4. Viewerでその文書を開き、ヘッダの項目が読取結果とキャンバスのハイライトに出て、明細の項目が出ないことを確かめる
5. `PUT /api/v1/config/document-types/{type_code}`で手順1の種別の項目の`description`を変え、もう一度IDP実行を行う。`engine_info`の定義のハッシュが変わることを確かめる
6. `POST /api/v1/documents/{document_id}/idp-runs/{run_id}/corrections`で、`items`に明細の値の修正（`field` / `index` / `property` / `value`）を送る。応答の新しい実行行で、修正した明細の値が変わり、その`confidence`がnullになることを確かめる

DIの種別で`array`を拒むことは、`engine`を`azure-di`にして`array`の項目を含む設定を送って確かめる。422 `validation-error`になり、`errors[].msg`に`azure-di does not support array fields`が含まれる。

アナライザの掃除は、`docs/azure/README.md`の「アナライザの掃除」の手順で行う。`--apply`を付けない実行では削除しない。

## 備考

- 数値の末尾に締めの記号がある値（例: `¥ 74,800 -`）は、正規化値がnullになる。抽出エンジンに依存しない正規化の問題として、 #218 で扱う
- 明細の表示と修正のUIは、 #216 で扱う
- 統合ブランチを検証環境へデプロイするときに、CUのリソースとデプロイが追加される
