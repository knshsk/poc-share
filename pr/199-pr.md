# 概要

APIは、文字列の入力に含まれるNUL（U+0000）・制御文字・双方向制御文字を検査していなかった。NULを含む入力は500になり、文書登録ではBlobだけが残って、同じ文書IDを登録し直せなくなることがあった。原本ファイル名に双方向制御文字が入ると、Viewerのヘッダーで文字の表示順を偽装できた。入力の種類ごとにAPIの境界で文字を止める形に直し、PDFのBlob名を内部IDから作るようにした。

Closes #166

## 変更内容

入力の種類ごとの扱いは次のとおり。対象の文字は、Unicodeの一般カテゴリCcの文字（U+0000〜U+001F、U+007F〜U+009F）と、Bidi_Controlプロパティの文字（U+061C、U+200E、U+200F、U+202A〜U+202E、U+2066〜U+2069）である（ADR-0026）。

- 原本ファイル名: `api/app/routers/documents.py`の`_original_filename`で、basenameを取り出した後に対象の文字を除く。除いた結果が空なら、空白だけの値と同じに扱う（`original_filename`が空なら`filename`を使い、どちらも空なら`null`）
- 文書登録の`document_id`: 対象の文字を含めば、ファイルを読む前に422 `validation-error`で拒否する。`document_id`はDI生応答のBlob名に使い、Azure Blob Storageは制御文字を含むBlob名を受け付けないためである
- 照会のキー: `find_document`と`get_config`は、NULを含むキーでは照会せず、該当なしを返す。パスの文書ID（14ルート）と種別コード（GET・PUT・DELETE）は404、文書登録の`document_type`は422 `unknown-document-type`になる。NUL以外の制御文字では照会を止めないので、制御文字を含む文書IDで以前に登録した文書も参照できる
- 公開閲覧のトークン: `api/app/routers/view_urls.py`で、失敗記録の`token_fragment`からNULを除いて保存する。応答は従来どおり404
- 本文の自由記述: 文書種別設定の`display_name`・`fields[].label`・`patterns[].label`・`patterns[].regex`と、人手修正の値（`fields`の値・`table_cells[].content`）に、pydanticの`pattern=r"^[^\x00]*$"`を付けた。NULを含むと422 `validation-error`になる。改行・TAB・双方向制御文字は受け付ける

PDFのBlob名は、呼出側の`document_id`ではなく、挿入の前に採番した内部ID（`documents.id`）から作る（`{tenant_id}/{id}.pdf`、ADR-0027）。Blobを保存してから行を挿入する順は変えていない。挿入に失敗した試行のBlobは残るが、名前は試行ごとに異なるので、同じ`document_id`の再登録を妨げない。同時登録の2本目も別の名前に保存した後で一意制約に当たり、冪等判定（200 / 409）に戻る。既存の行の`blob_ref`は旧形式のまま読み出せる。DI生応答のBlob名は変えていない。

- テスト
  - `tests/conftest.py`: テスト用の`InMemoryBlobStorage`を、Azureと同じく同名のBlobを上書きしない実装にした。Blobが残る不具合がテストで見つからなかったのは、フェイクが上書きを許していたためである
  - `tests/test_documents_api.py`: 原本ファイル名の文字の除去（対象外の隣の文字が残ることを含む）、文書IDの拒否（9種類の文字）、文書種別のNUL、Blob名が内部IDになること、挿入の失敗後の再登録、同時登録の2本目、パスのNULが404になること、NUL以外の制御文字を含む既存の文書IDの参照
  - `tests/test_tenant_isolation.py`: Blob名を文書IDで確かめていたassertを、テナントの接頭辞で確かめる形に変えた
  - `tests/test_document_type_configs_api.py`・`tests/test_idp_runs_api.py`・`tests/test_view_url.py`: 種別コードのNUL、本文のNUL、改行・TABを含む修正値の保存、トークンのNULと失敗記録
- API契約: `docs/api/openapi.json`を再生成した（patternの追加）。`viewer/src/api/schema.d.ts`は変わらない
- ドキュメント: `docs/architecture/api.md`・`docs/architecture/overview.md`・`docs/api/README.md`・`docs/data-model/documents.md`・`docs/data-model/view-tokens.md`・`docs/data-model/document-type-configs.md`・`docs/data-model/idp-runs.md`・`docs/azure/README.md`を更新した。ADR-0026（外部入力の文字の扱い）とADR-0027（PDFのBlob名を内部IDから作る）を追加し、ADR-0017の台帳（v1内で適用した破壊的変更）に文書IDの拒否を追記した

## 動作確認方法

自動テストは、`api/`で`uv run pytest`を実行する。

APIは、認証済みのアクセストークンを`$TOKEN`に入れて確かめる。

1. `filename`にNULを含むmultipartで文書を登録する。201が返り、`original_filename`は`ab.pdf`になる

```bash
printf -- '--b\r\nContent-Disposition: form-data; name="document_id"\r\n\r\nnul-check-1\r\n--b\r\nContent-Disposition: form-data; name="document_type"\r\n\r\nquotation\r\n--b\r\nContent-Disposition: form-data; name="file"; filename="a\x00b.pdf"\r\nContent-Type: application/pdf\r\n\r\n%%PDF-1.7\r\n--b--\r\n' | curl -s -X POST http://localhost:8000/api/v1/documents -H "Authorization: Bearer $TOKEN" -H 'Content-Type: multipart/form-data; boundary=b' --data-binary @-
```

2. 手順1のコマンドの`nul-check-1`を`nul\x01check`に変えて送ると、422 `validation-error`が返る
3. 次のコマンドは404を返す

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" 'http://localhost:8000/api/v1/documents/a%00b'
```

画面では、RLOを含む名前のPDFを登録して確かめる。

4. リポジトリのルートで`cp samples/quote-001.pdf "$(printf '見積\u202e書.pdf')"`を実行し、名前にRLOを含むPDFを作る
5. 文書選択ダイアログの登録タブで、このファイルを登録する。ヘッダーの文書タイトルは「見積書.pdf」と表示される。修正前は、RLOより後ろの文字が逆順になり「見積fdp.書」と表示される

## 備考

列の長さを超える入力で500になる事象（`User-Agent`・DIのエラーメッセージ）は #197 で、画面の登録エラーが英語のまま表示される事象は #198 で扱う。DIの出力にNULが含まれる場合は、実際のDIがNULを返すかを確かめていないため対象外とした。

Azureでは実行していない。Azure固有の挙動（上書きを許さない保存、制御文字を含むBlob名の拒否）への対応は、コードとAzure Blob Storageの命名規則に基づく。

これまで受け付けていた入力のうち、新たに422になるのは、制御文字・双方向制御文字を含む文書IDの登録だけである。Power Automateからの通常の登録の応答は変わらない。

挿入に失敗した試行のBlobは消さない（ADR-0027）。Blobは`{tenant_id}/`の下に残るので、テナント単位で消すときは一緒に消える。
