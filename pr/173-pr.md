# 概要

読込中の表示を共通のスピナーに統一し、ログイン直後のログインカードの一瞬表示・スケルトン・灰色のパルス・フッター上の隙間を無くす。Vue の起動前は起動スプラッシュを出し、API の応答を gzip で圧縮して、低速回線での初回表示を改善する。ページ画像の取得に失敗したページは紙面に失敗を表示する。

## 関連Issue

Closes #172

## 変更内容

- 共通のスピナー部品 `LoadingSpinner` と、遅延表示の判定 `utils/spinnerClock.ts` を追加した。0.3 秒未満で終わる読込ではスピナーを出さず、表示中のスピナーの続き（段階の切替）は待たずに出して点滅させない
- ログイン処理中（状態 `booting` / `callback`）は `vm.screen` を `loading` にし、ロゴだけのアプリバーと本文中央のスピナーを出す（ログインカードを出さない）。アプリバーを最初から出すので、文書画面へ移るときに `v-main` の上余白のアニメーション（2 ペインがアプリバーの下に潜り、フッターの上に隙間が出る）が起きない
- `DocumentView`（キャンバス・右ペイン）、`PublicView`（キャンバス）、`WorkPanel`（本文。タブに関わらず本文全体）のスケルトンをスピナーに置き換えた。Viewer から `v-skeleton-loader` の使用が無くなる
- `PageSvg`: 灰色のパルスをやめ、表示領域に入って画像を要求したページの白い紙面にスピナーを重ねる。取得に失敗したページ（`Model.imageFailed` / `vm.canvas.imageFailed`。文書の切替で消える）は警告アイコンと「ページを表示できませんでした」を出す。画像応答のスコープに読込の世代（`Model.loadGeneration`）を含め、同じ文書を開き直す前に出した要求の応答を、応答の順に関わらず捨てる
- 起動スプラッシュ: `viewer/index.html` の `#app` にスピナー（`v-progress-circular` と同じ見た目・同じ位置の素の HTML とインライン CSS）を置き、Vue の起動と同時に消える。ビルドでは CSS の `<link>` を `</body>` の直前へ移す（`vite.config.ts` の `moveStylesheetsToBody`）。head の stylesheet が届くまで画面全体の描画が止まるのを避け、CSS の到着前にスプラッシュを描く。body 内の stylesheet も module script の実行は待たせるので、Vue は CSS の適用後に起動する
- API: Starlette 同梱の `GZipMiddleware` で、500 バイト以上の JS・CSS・HTML・JSON を gzip で返す。PNG・woff2（Starlette の既定）と原本の PDF は圧縮しない。`Accept-Encoding: gzip` を送らないクライアントには従来どおり無圧縮で返す
- ドキュメント: `docs/viewer/display.md`（「読込中の表示」の節を新設）、`docs/viewer/result-panel.md`、`docs/architecture/viewer.md`、`docs/architecture/api.md`、`docs/azure/README.md`、`viewer/README.md`

## 動作確認方法

手元での確認:

1. `viewer` で `npm run dev` を起動し、testuser でログインして `?document_id=` 付きの URL の文書を開く。ログイン直後にログインカードが出ず、ロゴだけのアプリバーから文書画面へ移り、スケルトンが出ないこと
2. gzip: `viewer` で `npm run build` した成果物を `FACTONE_STATIC_DIR` に指定して API を起動し、`curl -sI -H 'Accept-Encoding: gzip'` で JS・CSS に `content-encoding: gzip` が付くこと

ヘッドレス Chromium での確認（本番ビルド、1440×900、`order-sample-001`）:

- 低速回線（Chrome DevTools の Fast 3G 相当: RTT 562.5ms・下り 180KB/s、キャッシュ無し、JS・CSS・JSON は gzip 後の大きさで転送）で、Keycloak のログイン送信から文書表示の完了までを計測した
  - `/callback` の読込開始から first paint 588ms、first-contentful-paint 884ms（起動スプラッシュ）。変更前は first paint 12.2 秒で、それまで白画面だった
  - 完了まで 11.3 秒（変更前 18.2 秒。圧縮なしの場合は 19.0 秒で、変更前と同程度）
  - 途中でログインカード・スケルトン・灰色のパルス・フッター上の隙間・スタイル未適用の画面が一度も出ない（撮影した全コマで検査）。`v-main` の上余白は 56px のまま動かない
  - スピナーは表示されてから完了まで途切れない（スプラッシュ → ロゴだけのアプリバー → 2 ペインの枠と 2 つのスピナー → 紙面と右ペイン本文のスピナー → 完成）
- 通信制限なし: ログインから文書表示までスピナーが一度も見えない（107 フレームすべて）。ログイン画面の `v-main` の上余白は 0 のまま
- ページ画像の要求を 500 にして同じ文書を開き直すと、紙面に「ページを表示できませんでした」が出てスピナーが消える
- 公開閲覧（`/view/{token}`。ページ一覧と画像を遅延つきの偽応答で返した）で、取得中はキャンバスと紙面にスピナー、取得後は紙面が出る
- gzip（ビルド成果物を配信する API をローカルで起動）: JS 956,870 → 277,919 バイト、CSS → 316,791 バイト、index.html と JSON も `content-encoding: gzip`。`Accept-Encoding` 無しは無圧縮、PNG・PDF は圧縮されない

## 備考

- body 内の stylesheet より前の要素（起動スプラッシュ）が先に描かれる挙動は Chromium で確認した。Firefox・Safari は未確認
- 起動スプラッシュの色は Vuetify の起動前に描くため `index.html` に直書きしている。テーマとの一致は `tests/boot-splash.test.ts` が検査する
- 静的ファイル（`FileResponse`）は 64KiB ずつ送るため、JS・CSS の gzip 圧縮はスレッドではなくイベントループ上で行われる。PoC の単一レプリカでは許容した
- 対象外（後続の候補）: 画面内の操作（実行履歴の選択・閲覧URL タブ・原本ダウンロード）の読込表示、フォントの差し替え、バンドルの縮小、静的ファイルのキャッシュヘッダ、JS の取得失敗時の案内
