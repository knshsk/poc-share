# 概要

原本DL失敗の通知方法を、画面全体の取得失敗画面からスナックバーに変える。あわせて、応答を待つ間はDLボタンを読込中の表示にし、連打しても取得要求が重ならないようにする。

## 関連Issue

Closes #191
Closes #193

## 変更内容

これまでは、原本DLが失敗すると状態が`documentError`に移り、画面全体が取得失敗画面になっていた。その後に再試行・参照・登録をすると、未保存の修正が確認なしに消えていた（#191）。また、応答を待つ間もボタンを押せたため、連打すると取得要求が重なっていた。閲覧URLの画面では、閲覧ログに`download`が要求の回数だけ記録されていた（#193）。

- 失敗の通知: `downloadFailed`は表示を変えず、`DocumentCanvas`のスナックバー「ダウンロードできませんでした」を出すだけにした。認証済みの画面と閲覧URLの画面の両方に出す。見た目は「修正を保存しました」と同じ`variant="tonal"`で、色を`error`にした。表示時間はVuetifyの既定の5秒で、閉じるイベントには既存の`snackbarClosed`を使う
- 連打の防止: Mediatorは応答を待つ間`downloading`を立て、重ねて届いた`downloadOriginal`を捨てる。ボタンは`loading`で読込中の表示にする。`disabled`にすると押した直後にキーボードのフォーカスが外れるので、付けていない。成功したときは新しいイベント`downloaded`で応答待ちを解き、文書を切り替えたときも解く
- 切替前の文書の`downloaded`・`downloadFailed`は、これまでどおりスコープで捨てる。切替前に押した原本は、応答が返れば今までどおり保存する
- テスト
  - `tests/mediator-document.test.ts`: 失敗しても`document`のままで、未保存の修正が残り、通知が出る（全画面エラーのテストを置き換えた）。応答を待つ間の`downloadOriginal`は捨て、完了後は再び取得する。切替前の文書の失敗では通知も出ず、切替で応答待ちが解ける
  - `tests/mediator-public.test.ts`: 失敗しても本文が残り、通知が出る
  - `tests/document-canvas.test.ts`: 応答待ちでボタンが`loading`になる。通知を閉じると`snackbarClosed`をbubbleする
- ドキュメント: `docs/architecture/viewer.md`・`docs/architecture/view-url.md`・`docs/viewer/display.md`の、ダウンロード失敗の表示と応答待ちの記述を更新した

## 動作確認方法

自動テストは、`viewer/`で`npm run test`を実行する。

1. 成功した実行結果がある文書を開き、読取結果の値を1つ書き換える。確定はしない。IDP実行は実際のDocument Intelligenceを呼ぶので、実行結果が既にある文書を使う
2. ブラウザの開発者ツールで、`/api/v1/documents/{document_id}/pdf`へのリクエストをブロックし、「原本ダウンロード」を押す。画面下に「ダウンロードできませんでした」が出て、5秒ほどで消える。文書の表示と書き換えた値はそのまま残る
3. ブロックを外し、開発者ツールで通信速度を落としてから「原本ダウンロード」を押す。応答を待つ間はボタンが読込中の表示になり、何度押してもNetworkタブの`.../pdf`は1件だけ増える。応答が返ると原本が保存され、ボタンは元に戻る
4. 閲覧URLの画面でも、手順2と手順3を同じく確かめる。ブロックの対象は`/view/{token}/pdf`で、失敗しても文書の表示は消えない。閲覧URLは、共有可の文書種別の文書で閲覧URLタブから発行する。発行するとローカルのDBに記録が残る

## 備考

画面での連打を防ぐ変更で、API側の制限は変えていない。有効な閲覧URLへの連続した要求（スクリプトからの要求など）は、これまでどおり止まらない。
