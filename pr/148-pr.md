# 概要

JWT の `tenant_id` クレームでテナントを解決し、文書・文書種別設定・閲覧 URL・IDP 実行ログをテナントで分離する。`documents` を内部 UUID 主キーにして同じ `document_id` を複数テナントで登録できるようにする。Keycloak realm 定義に属性・マッパーを追加し、テナント運用スクリプトを加える。

## 関連Issue

Closes #147

## 変更内容

- `core/auth.py`: `tenant_id` クレームを抽出。欠落・形式不正（`^[a-z0-9][a-z0-9-]{0,62}$` 外）は 403 `tenant-unresolved`
- 全ルーター: `settings.tenant_id` → `user.tenant_id`。`FACTONE_TENANT_ID` 廃止
- `documents.id`（UUID 主キー）と `(tenant_id, document_id)` UNIQUE。子テーブル `view_tokens` / `view_events` / `idp_runs` は `document_pk` へ張り替え（マイグレーション `d7e4b2c9a1f6`、データ移行テスト付き）
- 登録時の `document_id` に `/` `\` `.` `..` を拒否（Blob パスのテナント境界越え防止、422）
- 閲覧 URL の単体失効にテナント検査を追加（他テナントの ID は 404）
- `keycloak/realm/factone.json`: ユーザープロファイルに `tenant_id`、`factone-viewer` に user-attribute マッパー、`factone-integration` に hardcoded claim マッパー、`testuser` に属性
- `scripts/tenant.sh`（create / add-user / disable / enable）と `docs/develop-guide/tenant.md`
- pre-commit に shellcheck を追加
- ADR-0020 / ADR-0021、設計文書・データモデル文書・OpenAPI 更新

## 動作確認方法

1. ローカルスタックを初期化（`podman compose down -v && podman compose up -d`）し、`./scripts/local-stack/apply-keycloak-secrets.sh` を実行する（realm 再投入。既存 Keycloak データでは 403 になる）
2. `testuser` で Viewer にログインし文書が表示される（403 にならない）
3. `docs/develop-guide/tenant.md` の「動作確認」（`tenant.sh create` → M2M トークンの `tenant_id` → 文書種別登録 → `disable` で 401 → `enable`）を実施する

## 備考

外部契約の変更は 4 点: JWT に `tenant_id` 必須（欠落・形式不正は 403）、`document_id` にパス区切り文字を含む登録は 422、他テナントの閲覧 URL 単体失効が 404、`document_id` の一意性がテナント内に変更。パス・応答スキーマは不変。

Azure の稼働環境は realm 定義変更前にデプロイ済みのため、realm `factone` を削除して再インポートし、シークレット・リダイレクト URI を再設定する必要がある（`docs/develop-guide/deploy.md`）。
