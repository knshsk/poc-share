# 概要

文書 ID に Latin-1 の範囲外の文字（日本語など）を含む文書で、原本 PDF のダウンロード（`GET /api/v1/documents/{document_id}/pdf`・`GET /view/{token}/pdf`）が 500 エラーになる不具合を直す。`Content-Disposition` の `filename` に文書 ID をそのまま埋め込んでいたため、Starlette の応答ヘッダの符号化（latin-1）が失敗していた。

## 関連Issue

Closes #179

## 変更内容

- 原因: `pdf_response`（`api/app/routers/documents.py`）が `attachment; filename="{document_id}.pdf"` を組み立てていた。Starlette は応答ヘッダを latin-1 で符号化するため、範囲外の文字で `UnicodeEncodeError` になる。文書 ID に `"` を含む場合は、500 にはならないが引用の崩れたヘッダを返していた
- `filename` には、文書 ID の ASCII の印字可能文字以外と `"`・`\` を `_` に置き換えた代替名を入れる（例: 文書 ID `見積"1` → `___1.pdf`）
- 保存名（原本ファイル名、無ければ `{document_id}.pdf`）は常に `filename*=UTF-8''…`（RFC 5987）で渡す。これまでは原本ファイル名が無い文書に `filename` だけを返していた。Viewer のダウンロード（`viewer/src/utils/download.ts`）は `filename*` を優先して読むため、保存名は変わらない
- テスト（`api/tests/test_documents_api.py`）
  - 文書 ID が `見積"1` の文書で原本ダウンロードが 200 になり、`filename` が代替名、`filename*` が原本ファイル名になる。原本ファイル名が無いときは、`filename*` が文書 ID の保存名になる
  - 原本ファイル名が無い文書のヘッダの期待値を、`filename*` を含む形に更新した

ASCII の文書 ID で原本ファイル名がある文書は、ヘッダが変わらない。
