### 目的

Viewer は、コンポーネントがそれぞれ自前で API を呼び、読込中・実行中・保存中といった状態フラグを個別に持ち、未保存の変更のガードやキャンバスと右ペインの相互ハイライトのようなコンポーネントをまたぐ連携をストア経由で暗黙に行っている。

その結果、「どの状態でどの操作を受け付けるか」がコードのどこにも一箇所に書かれておらず、遅れて届いた応答の扱いや操作の二重実行の防止が、各コンポーネントのアドホックな実装に依存している。

**現状で起きている課題:**

- 応答順序の裁定（一覧取得中に IDP 実行が完了する、選択を切り替えた後に古い詳細応答が届く、など）が個々のコンポーネント内の変数に埋め込まれており、同種の不具合を直すたびに別の場所へ同じガードを足している
- 画面の状態遷移が暗黙のため、テストが「API をモックしてコンポーネントを描画し DOM を見る」形にしかならず、遷移の網羅や失敗経路の検証が重い
- 一つのコンポーネントがデータ取得・裁定・描画を兼ねるため、見た目の変更と挙動の変更が同じファイルで衝突する

**今後顕在化しそうな課題:**

- 操作や画面（一括操作、実行結果の比較、テナントごとの機能差など）が増えるほど状態フラグと横断連携の組み合わせが増え、レース条件と検証漏れを人手で追い切れなくなる
- 「実行中は文書を切り替えない」のような業務ルールをボタンの無効化だけで担保していると、キーボード操作や別経路からの操作で崩れる

そこで、状態と裁定を一箇所に集約する Mediator パターンを採用する。画面全体を一つのステートマシンとして扱い、コンポーネントは描画に関わるパラメータだけを受け取って表示し、操作はイベントとして上位へ伝え、状態機械が「その状態でその操作を受けるか、受けたら何をするか」を決める。これにより、状態遷移とレースの裁定を宣言的に一覧でき、挙動のテストを状態機械単体に集約でき、見た目と挙動の変更を分離できる。

### 作業内容

- `Root.vue` + `mediator/`（bubble / events / model / vm / machine / handlers）を新設し、全 View を `vm` prop + `useBubble()` に書き換える
- 4 つの Pinia store を Mediator に吸収し、`pinia` 依存を外す
- テストを Mediator 単体（状態遷移）+ View 単体（vm → DOM、DOM → bubble）に再編する
- `docs/architecture/viewer.md` / `docs/viewer/*` / `viewer/README.md` を更新し、ADR-0023 を起票する
